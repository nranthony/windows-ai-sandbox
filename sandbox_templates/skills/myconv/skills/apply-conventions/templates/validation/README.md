# validation/ — evidence of measured behaviour

What this system was measured to do, against what, and when. Committed on purpose: these
files are not build output and not scratch. They are the record behind any accuracy claim
this repo makes, and they are what a CI gate reads.

Recorded as **ADR-0009** in the conventions repo (`docs/adr/0009-validation-evidence-tier.md`)
— deliberately not a link, because this file ships inside a plugin payload and a relative
path out of it resolves nowhere.

## The two rules

Authority is encoded in the filename. Everything else here follows from these:

- **Nothing regenerates `expected.json`.** It is hand-edited, and it is what the gate
  enforces. A regeneration script that writes it is a bug.
- **Nobody hand-edits `measured.*`.** They are the record of a run. A hand-edit falsifies a
  record.

The split is what keeps a threshold change *visible*: because the gate reads `expected.json`,
regenerating a record cannot change what passes. Loosening a threshold is a one-line diff to a
named file with a justification beside it. Nothing prevents it — it just cannot happen
quietly.

## What exists

| Corpus | What is measured | Gate | Regenerate with |
|---|---|---|---|
| `example-corpus` | *(one line: what this corpus tests)* | *(which check reads its `expected.json`)* | `<the exact command>` |

Keep the regeneration command exact and current. The end state for a record nobody can
refresh is folklore: it stops being evidence and becomes a claim.

## Layout

```
validation/
└── <corpus>/
    ├── expected.json    # hand-edited. Thresholds the gate enforces. Small.
    ├── measured.json    # regenerated. The record of the last run.
    └── measured.md      # regenerated by the same command. Human-readable table.
```

One directory per corpus — that is the unit a reader asks about and the unit that changes
independently. If one corpus carries several independent harnesses, nest one level:
`<corpus>/<harness>/`.

### `expected.json`

Thresholds and tolerances only, never a mirror of the measurements. **Every threshold carries
a `why`**, because a number with no stated reason is exactly what gets loosened silently
later:

```json
{
  "sensitivity": {
    "min": 0.995,
    "why": "floor agreed in ADR-00XX; record 207's flutter run is the binding case"
  }
}
```

JSON has no comment syntax — `why` is the sanctioned place for the reasoning, so don't reach
for `//`. A required field also does what a comment cannot: a gate can quote it in the failure
message, so a breach reports *why the floor exists* rather than just that a number moved.

### `measured.json`

Opens with provenance, then the results:

```json
{
  "provenance": {
    "generated": "YYYY-MM-DD",
    "commit": "<short sha of the code that produced this>",
    "command": "<the exact command that regenerates this file>",
    "corpus": "<corpus name and version identifier>",
    "corpus_digest": "sha256:<digest of the corpus as used>"
  },
  "records": {}
}
```

`command` and `corpus` are required. `corpus_digest` is required where the corpus has no
authoritative version identifier — without it, an apparent regression and an unnoticed data
change are indistinguishable after the fact. Where the corpus ships a stable published
version, the digest may lag: it is then guarding local corruption and partial downloads.

`measured.md` repeats the provenance as a header so the human-readable artifact is
self-dating, and **one command writes both files** — generating them separately is how the
table drifts from the data.

Keep `measured.json` reviewable **as a diff**. Past that size, record aggregates here and let
the harness regenerate per-record detail on demand.

## Adding a corpus

1. Create `validation/<corpus>/`.
2. Write `expected.json` by hand — only the numbers the gate should fail on, each with a `why`.
3. Run the harness to produce `measured.json` and `measured.md`.
4. Add a row to the table above, with the exact regeneration command.
5. Point the gate at `expected.json`.

Step 2 is the one that takes thought: **which numbers does the gate fail on, versus which are
recorded for a reader?** If one file has been doing both jobs, this question has never been
asked. Answer it once, here, rather than repeatedly and after the fact.

## What does not belong here

- **Golden-output snapshots** → `tests/`. They live beside their consumer and have no audience
  beyond the test runner.
- **Ground-truth labels themselves** → wherever the corpus lives. They are input data, not
  evidence of behaviour.
- **Performance and latency benchmarks** — environment-dependent, so a committed record is
  usually noise rather than evidence.
- **External reports and scan baselines** — produced outside the repo and not regenerable from
  it, so the two rules above cannot apply.

---

*`example-corpus/` is a placeholder. Rename it to a real corpus or delete it — its thresholds
are set to values nothing can pass, so an unreplaced template fails loudly instead of
resolving silently.*
